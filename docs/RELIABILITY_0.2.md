# Надёжность 0.2.0-alpha

Версия продолжает план 0.2.0 из GitHub: векторы и строгие handshake-проверки,
пулы соединений, ротация, ограниченные повторы, отмена и нагрузочные испытания.
Эталон остаётся Flowseal v1.11.2 (`307a384ab7f522e34bb1a045884d0bd90f40bee5`).
Зависимости, package/applicationId и minSdk 35 сохранены.

## Пул свежих WSS-подключений

- В пул попадает соединение после TLS и HTTP Upgrade, **до** MTProto init.
  Оно не содержит состояния шифрования клиента и выдаётся только один раз.
  Активные и завершённые MTProto-сессии в пул не возвращаются.
- Пул только для прямых WSS-маршрутов DC 2/4: не более одного подключения
  на пару IP/имя, четыре в сумме, два фоновых connect-потока и ограниченная очередь.
  Media и обычные маршруты используют свои имена; таблица DC не изменена.
- Подготовка начинается после успешного реального клиентского подключения.
  При запуске listener сеть без спроса не прогревается.
- Возраст — до 30 с. Просроченные сокеты закрываются; при отсутствии спроса
  они не заменяются бесконечными фоновыми подключениями. Проверка возраста есть
  как при периодической ротации, так и при получении из пула.
- Перед MTProto init выполняется Ping с новым nonce и проверяется совпадающий
  Pong. Close, данные до init, неверные кадры или тайм-аут закрывают сокет;
  допускается новая попытка того же маршрута в пределах общего срока.
- Каждая фоновая попытка ограничена 8 с. Сокеты регистрируются до connect/TLS,
  закрываются при отмене; запоздавшие результаты предыдущей сети не принимаются.

Это нативная политика Android по мотивам `proxy/pool.py` upstream, а не буквальная
копия: upstream использует иной возраст/размер пула и более длительный backoff.
Native-пул заполняется по спросу, чтобы ограничить лишнюю фоновую работу.
**TCP и пользовательское WSS-реле не прогреваются:** реле 0.1.3 требует init
за 10 с, поэтому хранить его пустые соединения 30 с было бы некорректно.

## Контролируемые повторные подключения

Отказы setup учитываются отдельно для каждого WSS-имени, TCP DC и relay DC.
Паузы — 1, 2, 4, 8, 16, затем максимум 30 с по монотонным часам. После паузы
разрешена одна проверочная попытка; успех снимает backoff. Ошибка более старой
параллельной попытки не отменяет более новый успех. Смена сети очищает backoff.

Прямой режим сохраняет WSS → TCP; relay-only сохраняет только выбранное реле.
Если маршруты на паузе, приложение показывает это отдельно. Нет спящих
клиентских потоков, бесконечных циклов retry или перепроигрывания пакетов после
начала передачи. Для установленной сессии восстановлением занимается Telegram.
Одна сессия по-прежнему имеет свои четыре AES-CTR направления.

## Проверки

JVM-тесты покрывают одноразовые leases, общий лимит, ротацию без лишнего reconnect,
отмену/тайм-аут connect, поздние сокеты, корректный Pong, отказ при ранних данных,
backoff и reset. Прежние Flowseal-векторы сохранены.

Нагрузочный стенд использует настоящий loopback TCP и TLS/WSS, независимый
Java AES-CTR peer, четыре одновременных клиента, ef/ee/dd, несколько пакетов на
сессию, фрагментированный ввод, искусственные WSS-отказы и периодические сбросы
сети. Он проверяет ответные байты и ограничения, сохраняет только числовую
статистику. Это имитация удалённого Telegram transport, не Telegram E2E.

```bash
# Обычный прогон: soak по умолчанию 2 с.
./gradlew --no-daemon :app:testDebugUnitTest :app:lintDebug :app:assembleDebug
# Длительность стенда 1–3600 с; CI использует 60 с.
./gradlew --no-daemon -PsoakSeconds=180 :app:testDebugUnitTest :app:lintDebug :app:assembleDebug :app:assembleDebugAndroidTest
```
