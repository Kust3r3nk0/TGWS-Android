# TGWS-Android 0.3.5-alpha — Media Upload Fix (рабочая ветка)

**Статус:** разработка; код диагностики ещё не проверен на телефонах. Стабильная передача
HD/голосовых/видеокружков через Cloudflare Worker **не подтверждена**. Не публиковать стабильный релиз.

## Наблюдения владельца (Android 16, LTE, Cloudflare Worker)

- Telegram: текст и SD-фотография отправляются; HD-фотография зависает в загрузке.
- 0.3.4-alpha, собственное WSS-реле (Cloudflare Worker); HTTP/2 media в этом режиме не используется.
- Snapshot: media DC1 был READY, но это лишь успешно завершённый setup, не доставка файла.
- 6 активных сессий Android не доказывают превышение `maxSessions=8`.
- В Worker есть предел 16 МиБ двустороннего трафика одной сессии, очередь 4 МиБ,
  64 ожидающих сообщений и максимум 4 сессии на isolate.
  Ранее показанные общие Android-счётчики не позволяют установить срабатывание конкретного предела.

## Изменения первого этапа

1. Cloudflare Worker: закрытия сопровождаются постоянными безопасными категориями
   `BYTE_LIMIT`, `QUEUE_LIMIT`, `MESSAGE_LIMIT`, `FRAME_LIMIT`,
   `INIT_TIMEOUT`, `WRITE_TIMEOUT`, `TCP_ERROR`, `TCP_EOF` и др.
   Ни URL/токен, ни IP, ни данные сообщения в reason не выводятся.
2. Android: принимает коды закрытия через WSS как типизированное исключение, причину
   только из разрешённого списка. Ошибка маршрута различает RELAY и SESSION.
3. Экспорт: `route_sent`/`route_received` на маршрут (накопительные счётчики
   **с момента запуска приложения**, не на отдельный файл), `close_code` и
   `close_reason`. Закрывшийся последний маршрут получает состояние CLOSED,
   а не остаётся READY. Данные в отчёте не содержат секретов.
4. Тесты: обработка статусов, анонимность экспорта, WebSocket Close frames,
   последовательная отправка 18 МиБ в Worker c увеличенным *тестовым* бюджетом,
   отдельно проверяется ограничение трафика.
5. Версия APK: 0.3.5-alpha, minSdk 36 (Android 16+).

**Ограничение:** Workers WebSocket API не предоставляет `drain`/надёжного
backpressure для отправки в сторону Android. Поэтому production-лимит 16 МиБ
**не поднят**; автоматические тесты с тестовым лимитом 24 МиБ не
доказывают, что реальный Worker способен долго передавать HD.
Снять ограничение без flow control нельзя. Повторную отправку старых
MTProto ciphertext-пакетов запрещено добавлять для «исправления» upload.

## Проверка владельцем после зелёного CI

1. Скачать APK именно с PR, проверить версию, commit и SHA-256.
   Не удалять предыдущее приложение ради смены подписи.
2. Обновить **свой** опубликованный Cloudflare Worker из проверенного build
   (или согласовать развёртывание), оставив прежний токен/URL. Не публиковать токен.
3. В Telegram с включённым TGWS отправить текст, SD, небольшую HD-фотографию,
   голосовое и кружок, затем файл 1/5/10/20 МиБ.
4. При зависании сохранить два экспорта (во время передачи и спустя 20–30 с),
   сравнить `route_sent`, `route_received`, `close_code`, `close_reason`,
   `dc`, `media`, `attempts`, `state`. Не прикладывать текст сообщений,
   реальный адрес реле и ключ.
5. Повторить отдельно на Wi-Fi и LTE. Отличать закрытие Worker от сетевой
   блокировки и сбоя Telegram.

## Решение по результатам

- `BYTE_LIMIT` → требуется безопасный потоковый контроль (протокол с credit/ack,
  ограниченной очередью) либо Node.js WSS-реле; не просто увеличение byte budget.
- `QUEUE_LIMIT`/`MESSAGE_LIMIT` → определить пики входных сообщений и
  реализовать безопасный backpressure, сохранив порядок пакетов.
- `WRITE_TIMEOUT`/`TCP_ERROR` → исследовать маршрут Worker → DC и тайм-ауты.
- Нет закрытия, но счётчики стоят → исследовать возможное зависание MTProto framing
  или Telegram upload, сопоставить оба направления и проверку на альтернативном реле.
