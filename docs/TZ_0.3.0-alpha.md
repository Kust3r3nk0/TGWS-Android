# Техническое задание для Codex
## TGWS-Android 0.3.0-alpha — Extended Transport & Android Optimization

**Репозиторий:** https://github.com/Kust3r3nk0/TGWS-Android
**Базовая версия:** `0.2.0-alpha` (проверить актуальный HEAD перед работой)
**Эталон:** https://github.com/Flowseal/tg-ws-proxy, закреплённая в проекте версия v1.11.2, commit `307a384ab7f522e34bb1a045884d0bd90f40bee5`.
**Платформа:** Android 16+ (minSdk 36), Kotlin, Jetpack Compose / Material 3.

### 1. Цель и границы

Объединить ранее запланированные этапы `0.3.0 — расширенные транспорты` и `0.4.0 — оптимизация Android` в **один релиз `0.3.0-alpha`**. Доработать существующее приложение, а не создавать новый проект. Его назначение остаётся прежним: локальный MTProto WebSocket-прокси для Telegram, **не системный VPN**. Не добавлять `VpnService`, захват системного трафика, Python в APK или обязательный внешний сервис.

До изменений прочитать `AGENTS.md`, `ROADMAP.md`, `docs/DEVELOPMENT_BASELINE.md`, `docs/MOBILE_NETWORKS.md`, `docs/RELIABILITY_0.2.md`, текущие Gradle-файлы, соответствующие Kotlin-модули и тесты. Сохранить `applicationId`, пользовательские настройки, русскоязычный интерфейс, английские строки и существующую функциональность: Obfuscated2 ef/ee/dd, AES-CTR, WSS → TCP, relay-only, Keystore, Foreground Service, WSS-пул и bounded backoff. Не снижать уровень проверки TLS.

### 2. Расширенные транспорты

**2.1. Fake TLS и маскировка**

- Реализовать совместимый с закреплённым эталоном Flowseal режим MTProto Fake TLS (в том числе `ee` secret, если этот режим предусмотрен эталоном); проверить точный wire-format по исходникам и тестам upstream, не подменять его обычным TLS.
- Добавить валидируемую настройку доменного имени для Fake TLS и корректное кодирование/декодирование секретов, совместимое с Telegram и upstream. Исключить произвольные неподтверждённые допущения о handshake.
- В интерфейсе разграничить **MTProto Fake TLS** и **реальный TLS/WSS**: Fake TLS сам по себе не удостоверяет удалённый сервер и не заменяет проверку сертификата.
- Сохранить работу стандартных `ef`/`dd` режимов, импорт/генерацию ссылки Telegram, независимые криптографические контексты и корректную обработку плохих или неполных handshake. Не объявлять гарантированное прохождение сетевых ограничений.

**2.2. Cloudflare Proxy и Worker fallback**

- Использовать уже существующий клиент Worker-совместимого WSS-реле из `0.1.3-alpha`: расширять, а не дублировать.
- Реализовать отдельно: (а) Cloudflare Proxy по совместимой с Flowseal схеме адресации и выбора доменов; (б) fallback через конфигурируемые Cloudflare Workers/WSS endpoints; (в) механизм выбора доступного маршрута с ограниченной ротацией и backoff.
- Не путать Cloudflare Proxy, Cloudflare Worker и собственное WSS-реле — это разные режимы, с различной конфигурацией и требованиями к серверу.
- Предусмотреть безопасный конфигурируемый список доменов/Worker endpoints, строгую валидацию, TLS с проверкой имени, конечные тайм-ауты, ограничение попыток, отсутствие бесконечных переподключений. Автоматическое обновление доверенного списка — только по HTTPS, с проверкой результата и атомарной заменой; при ошибке сохранять последний рабочий список.
- Для совместимого Worker соблюдать контракт `/apiws?dst=...&dc=...`, допустимые Telegram DC/адреса и relay initialization по закреплённому upstream. Не создавать открытый прокси для произвольных адресов (SSRF/open relay); на серверной стороне ограничивать назначения, ресурсы и доступ.
- Сохранить явный **relay-only**: при его выборе прямой WSS/TCP fallback запрещён. Для отдельного режима «Автоматический Cloudflare» использовать согласованный с Flowseal порядок доступных методов Worker → Cloudflare Proxy → TCP, только когда соответствующий метод настроен/разрешён; не менять маршрут после начала передачи MTProto-пакетов.
- Добавить в `docs/` пример конфигурации и документацию по собственному Worker/Cloudflare-прокси, различая локальную проверку, фактический деплой и внешний end-to-end. Никаких встроенных чужих учётных данных или фиктивных «работающих» адресов.

**2.3. HTTP/2 и медиатрафик**

- Реализовать совместимый с Flowseal транспорт HTTP/2 **только для маршрутов/серверов, которые действительно поддерживают соответствующий протокол**; не пытаться считать произвольный Telegram DC HTTP/2 endpoint.
- Для поддерживаемого Cloudflare media-маршрута корректно согласовать ALPN `h2`, реализовать потоковую двустороннюю передачу, ограничение буферов, backpressure, отмену, обработку `RST_STREAM`/`GOAWAY` и закрытие ресурсов.
- Учесть media DC и знаковые значения DC согласно upstream. При неподдерживаемом сервере или отказе HTTP/2 выполнить контролируемый fallback на разрешённый WSS/другой маршрут **до передачи пользовательских данных**, без повторной отправки уже переданных пакетов.
- Не нарушать потоковые AES-CTR состояния, порядок байтов и фрейминг Abridged/Intermediate/Padded Intermediate.

**2.4. Диагностика маршрутов**

- Добавить в интерфейс отдельный экран или раздел «Диагностика»: локальный listener, текущая сеть, тип транспорта, DC/media DC, этап подключения, состояние маршрута (`не проверен`, `доступен`, `подключение`, `backoff`, `недоступен`), категория последнего сбоя, число активных сессий и счётчики трафика.
- Различать «локальный прокси запущен» и «удалённый маршрут успешно проверен»; не выдавать потенциальный маршрут за работающий без реального handshake.
- Предусмотреть безопасную ручную проверку маршрутов с лимитом частоты; фиксировать реальные результаты/время проверки, а не оценочные цифры. Никаких тел сообщений, ключей, URL с токенами, MTProto secrets или содержимого пакетов в логах и экспорте.

### 3. Android и сетевые условия

**3.1. IPv4, IPv6 и IPv6-only**

- Корректно работать в IPv4-only и dual-stack сетях; поддерживать IPv6-only, когда доступен соответствующий маршрут через AAAA, NAT64/DNS64 либо системные механизмы Android.
- Не предполагать, что жёстко заданный IPv4 DC всегда достижим в IPv6-only. Разрешать домены через активный Android `Network` и системный resolver; учитывать доступность NAT64/464XLAT, не выдумывать IPv6-адреса Telegram и не внедрять собственный NAT64 без основания.
- При недоступности всех маршрутов сообщать причину и предлагать настроенный доменный WSS/Worker-канал, а не зависать в бесконечном retry. Тестировать IPv4, IPv6, dual-stack, IPv6-only с NAT64 и без доступного совместимого выхода.

**3.2. Wi-Fi ↔ мобильная сеть**

- Использовать `ConnectivityManager`/`NetworkCallback` и актуальный `Network` для DNS и сокетов, исключая гонки при смене сети. При смене default network отменять устаревшие соединения, WSS-пул, DNS-кеш маршрута и backoff предыдущей сети; освобождать сокеты.
- Пока foreground proxy включён пользователем, автоматически возобновлять готовность принимать новые соединения и строить новые удалённые маршруты после появления сети. Не пытаться «бесшовно» продолжить старую MTProto-сессию на новом IP и не повторять шифрованные байты. Пересоздание сессии выполняет Telegram.
- Учитывать быстрые переключения, потерю обеих сетей, captive portal, отсутствие validated Internet и поздние callbacks. Не создавать дубликаты listener, фоновых задач или уведомлений.

**3.3. Энергосбережение и фоновая работа**

- Сохранить пользовательский запуск и остановку Foreground Service, корректный тип сервиса и уведомление для Android 16+; соблюдать ограничения ОС и не обходить Doze/системные разрешения скрытно.
- Убрать бесконечный polling, лишние wake locks и прогрев маршрутов без клиентского спроса. Сохранить ограниченную политику `0.2.0-alpha`: подготовка WSS по потребности, одноразовые leases, лимиты размера/возраста, cleanup при stop и смене сети.
- После остановки не оставлять активных сокетов, callbacks, корутин, задач и уведомлений; после убийства процесса восстанавливаться только в границах разрешённого Android lifecycle. Показать понятные состояния остановки/ограничения работы в фоне.

### 3.4. Российские операторы мобильного интернета: МегаФон, МТС, билайн и T2

**Задача:** обеспечить операторо-независимую работу TGWS-Android в реальных сетях четырёх крупных российских операторов и предоставить диагностику, позволяющую воспроизводить отличия мобильного доступа. Это **справочные параметры и сценарии тестирования, а не встроенные профили обхода блокировок**. Нельзя обещать поддержку конкретного протокола, IPv6 или удалённого маршрута у всего оператора: фактическая доступность зависит от региона, базовой станции, SIM/eSIM, тарифа, APN и текущей конфигурации сети.

#### 3.4.1. Справочник идентификаторов и APN

| Оператор / бренд | Основной PLMN (MCC + MNC) | Рекомендуемый справочный APN для обычного интернета | Логин / пароль (из официальных инструкций) | Важные уточнения |
|---|---|---|---|---|
| **МегаФон** | `25002` (`250` + `02`) | `internet` | **Не задавать автоматически**: использовать конфигурацию SIM/Android, не подставлять выдуманные значения | В публичном справочнике также встречается `25014`; не делать вывод об операторе только по одному коду. `internet` упомянут в официальной документации МегаФона; актуальный APN конкретной SIM имеет приоритет. |
| **МТС** | `25001` (`250` + `01`) | `internet.mts.ru` | `mts` / `mts` | Официальные параметры ручной настройки; стандартный APN устанавливается автоматически при активации SIM. |
| **билайн** | `25099` (`250` + `99`) | `internet.beeline.ru` | `beeline` / `beeline` | В примере официальной инструкции: `PAP`, тип APN `default`, протокол APN `IPv4`; **это не доказательство**, что у всех абонентов нет IPv6. Применять параметры только по указанию ОС/оператора. |
| **T2 (ранее Tele2)** | `25020` (`250` + `20`) | `internet` | Поля оставляют пустыми | Официальная инструкция указывает `internet`; при ручной настройке также может потребоваться APN type `default`, MCC `250`, MNC `20`. |

**Смысл справочника:** MCC/MNC служат ориентиром для показа названия и диагностики, а APN — справочной информацией для человека. Приложение **не должно менять настройки APN**, переключать SIM, задавать произвольные DNS, выбирать частоты/базовые станции или устанавливать новый APN вместо системного. На обычном Android такие операции часто ограничены системными привилегиями и не относятся к назначению прокси. При MNP (переносе номера), MVNO, роуминге, нескольких SIM/eSIM, дополнительном PLMN и переименовании бренда возможны несовпадения; всегда доверять фактическим данным активной сети, а не фиксированной таблице. Не идентифицировать оператора по телефонному префиксу.

- МТС, официальные настройки: https://support.mts.ru/mts_mobilnyy_internet/nastroiki-mobilnogo-interneta/kak-nastroit-internet-na-telefone
- билайн, официальные настройки: https://moskva.beeline.ru/customers/support/mobile/mobilniy-internet/nastrojki/nastrojka-telefona/
- T2, официальные инструкции: https://karta.t2.ru/journal/article/how-to-set-up-internet и https://mycard.t2.ru/help/article/android-setup

#### 3.4.2. Фактические сетевые параметры — определять динамически

Для **каждого** из четырёх операторов предусмотреть одинаковый набор полей в диагностике (только в объёме, доступном приложению без избыточных разрешений):

| Группа | Поля/состояния | Требование к реализации |
|---|---|---|
| Определение оператора | название активного оператора; зарегистрированный PLMN; при доступности — оператор SIM | Использовать `TelephonyManager` и сведения о **действующей data-SIM** при наличии доступа; различать SIM-оператора и оператора регистрации в роуминге. Не скрывать значение «неизвестно». |
| Мобильная радиосеть | 2G / 3G / LTE / LTE+ / NR (5G) / неизвестно | Показывать только фактическую информацию, если Android её предоставляет; не считать 5G доступным на основании тарифа, значка или имени оператора. Не запрашивать `READ_PHONE_STATE`, если достаточны доступные без разрешений API. |
| Тип текущего доступа | `CELLULAR` / `WIFI`, default Network, validated Internet, metered/roaming если доступны | `ConnectivityManager`, `NetworkCapabilities`, события сети; использовать фактический маршрут приложения, не только наличие SIM. |
| Адресация | IPv4, IPv6, dual-stack, IPv6-only, NAT64-префикс при наличии | Получать `LinkProperties`, адреса/маршруты и `getNat64Prefix()`; **не путать наличие локального IPv6 с гарантированной доступностью внешних IPv6 endpoints**. |
| DNS | текущие DNS-серверы, Private DNS при доступности, результаты A/AAAA для выбранного тестового домена | Использовать `LinkProperties` и resolver активной сети; **не хранить фиксированные DNS «МТС/билайн/МегаФон/T2»** — они зависят от сети и пользователя. |
| Доступность маршрутов | TCP, TLS/WSS, настроенный Worker/CF, H2/media, DNS/TLS/HTTP ошибки | Отображать фактически пройденный handshake/тест и состояние каждого разрешённого маршрута. Не проверять неразрешённые адреса. |
| Диагностика качества | latency только для конкретного испытания и узла, время ответа DNS/TCP/TLS, тайм-ауты, число попыток, статистика сессий | Измерять монотонными часами и указывать этап замера; **не подменять ping Telegram результатом TCP handshake**, не обещать скорость без теста передачи данных. |
| Ограничения сети | CGNAT/публичный IP — лишь когда это действительно проверено, captive portal, разрыв, операторские/тарифные ограничения | Не объявлять CGNAT, DPI, блокировки или отсутствие IPv6 «по бренду». При отсутствии независимого подтверждения писать «причина не определена». |

**Технические правила:**

1. Для IPv4/IPv6 и смены сетей использовать `ConnectivityManager`, `Network`, `NetworkCapabilities`, `LinkProperties`, `NetworkCallback`; сетевые соединения должны быть привязаны к актуальной сети или корректно пересоздаваться после её изменения.
2. Для операторских сведений применять `TelephonyManager` и, когда требуется, `SubscriptionManager` с обработкой Android permissions, двух SIM/eSIM и отсутствия телеком-модуля. `getSimOperator()` и `getNetworkOperator()` отражают **разные** сущности; не считать их взаимозаменяемыми.
3. Если доступ к полю требует разрешения, проверить официальное Android API, применять минимально необходимое разрешение и понятный запрос; при отказе показывать «недоступно» и не ломать прокси. Никогда не требовать доступ к SMS/звонкам/контактам, IMEI, IMSI или геолокации для базовой работы.
4. Операторские особенности не должны появляться как `if (carrier == MegaFon)` в транспортном ядре. Выбирать маршрут по реально измеренным `NetworkCapabilities`/DNS/ошибкам и настройкам пользователя, а не по имени оператора.
5. Никакой автонастройки или принудительного изменения системного APN, DNS, IPv4/IPv6, сети, SIM или тарифа. В UI при необходимости дать только ссылку на официальную инструкцию оператора.
6. В локальном журнале и отчёте **не сохранять** телефонный номер, идентификатор SIM, IMSI/ICCID/IMEI, Cell ID, точное местоположение, публичный IP, секреты и полный URL реле с токеном. Сведения о PLMN и типе сети показывать опционально; при экспорте обезличивать и давать пользователю предпросмотр.

#### 3.4.3. Матрица сценариев для каждого из четырёх операторов

Каждый набор сценариев применим **отдельно к МегаФону, МТС, билайну и T2**, только если реальная тестовая SIM, регион и соответствующая сетевая среда доступны. Отсутствующий режим фиксируется как `N/A — условия недоступны`, а не `PASS`.

| ID | Сценарий | Что должно проверяться |
|---|---|---|
| RU-01 | Вход в мобильный интернет LTE | listener активен, Telegram подключается, сообщения отправляются/принимаются, WSS/relay/TCP ведут себя согласно выбранному режиму. |
| RU-02 | 2G/3G/LTE+/5G при наличии | Работа при доступной радиотехнологии; не требовать 5G и не симулировать его как реально проверенный. |
| RU-03 | IPv4-only | DNS и TCP/TLS/WSS, Media, диагностические ошибки, отсутствие ложных успешных соединений. |
| RU-04 | Dual-stack IPv4/IPv6 | DNS A/AAAA, выбор доступного адресного семейства, отсутствие зацикливания на недоступном IPv6. |
| RU-05 | IPv6-only и NAT64/DNS64 | Корректная работа при наличии совместимого механизма, отчётливо определённый отказ при его отсутствии. |
| RU-06 | IPv6-сеть без доступного маршрута к Telegram | Сообщение с причиной/этапом ошибки; не переходить на неразрешённый транспорт и не создавать вечные подключения. |
| RU-07 | Wi-Fi → мобильная сеть и обратно | Снятие старых соединений/запросов, отсутствие двойного listener, новые MTProto-сессии без replay. |
| RU-08 | Потеря сигнала, режим полёта, восстановление | backoff, отмена callbacks, очистка DNS/pool, появление новых сессий после возвращения интернета. |
| RU-09 | DNS-ошибка, TLS-ошибка, недоступность Worker | Корректная классификация и информирование; строгая проверка сертификата; relay-only без скрытого direct fallback. |
| RU-10 | Текст, фотографии, видео, крупные файлы Telegram | Проверить обе стороны передачи данных, media DC, H2/WSS fallback и отсутствие зависаний. |
| RU-11 | 30–60 минут работы с экраном выключен | Foreground Service, отсутствие необоснованных фоновых соединений, предсказуемое восстановление при ограничениях ОС. |
| RU-12 | Dual-SIM/eSIM, выбор data-SIM и смена оператора | Диагностика показывает активную сеть, а не случайную SIM; старый маршрут не остаётся привязанным к прежней сети. |
| RU-13 | Региональный роуминг/MVNO/переход в другую PLMN (если доступно) | Не ошибаться в отображении SIM-оператора и оператора регистрации; не ломать маршрутизацию из-за несовпадения PLMN. |
| RU-14 | Переключение режимов прямой WSS/TCP, собственного relay, CF/Worker | Проверить отдельные режимы и пользовательский приоритет; не подменять режим и не отправлять данные повторно. |

**Обязательный принцип покрытия:** JVM/emulator/CI должны проверять *операторо-независимую логику и моделируемые сценарии для всех четырёх карточек операторов*. Они **не могут доказать фактическую работу в сетях четырёх операторов**. Физические проверки проводит владелец проекта на доступных ему SIM и сети; остальные операторы остаются `NOT TESTED` до получения реальных воспроизводимых результатов. От Codex не требуется покупать SIM, менять оператора, выходить в сотовую сеть или ожидать результатов владельца для завершения текущего этапа.

### 5. Тестирование и критерии приёмки

Обязательно добавить детерминированные JVM unit/integration tests и Android instrumentation tests:

1. Совместимость ef/ee/dd, handshake Fake TLS и побайтовые векторы upstream; отклонение повреждённых или неполных сообщений.
2. Cloudflare/Worker routing: корректные DC/media, TLS, тайм-ауты, секреты, ротация/backoff, relay-only без утечки в прямой маршрут; отсутствие replay после частичной передачи.
3. HTTP/2: несколько одновременных потоков, двусторонние байты, flow control/backpressure, отказ ALPN, RST_STREAM/GOAWAY, отмена и fallback.
4. IPv4/IPv6/IPv6-only и NAT64: успешные маршруты и предсказуемые ошибки при отсутствии совместимого выхода.
5. Wi-Fi ↔ LTE/5G, network loss, восстановление, устаревшие callbacks, множественные старты/остановки, исключение утечек ресурсов.
6. Справочник МегаФон / МТС / билайн / T2 и корректное определение действующей data-SIM/PLMN: тесты на известные и неизвестные коды, дополнительные PLMN, роуминг/MVNO, отсутствие разрешения, пустые ответы API; моделируемая матрица RU-01—RU-14 по доступным сценариям.
7. Lifecycle Android 16/17, foreground notification, остановка сервиса, обновление со старой версии и сохранение пользовательских настроек.
8. Нагрузочный прогон с локальными TLS/WSS/TCP/H2 тестовыми узлами: параллельные MTProto-сессии, media, паузы, фрагментация, отмена, ошибки маршрутов; без утечек и роста числа фоновых соединений.

Запустить минимум:

```bash
./gradlew --no-daemon :app:testDebugUnitTest :app:lintDebug :app:assembleDebug :app:assembleDebugAndroidTest
```

Проверить существующую CI-матрицу Android API 36/37 и её реальные JUnit-результаты; по возможности выполнить `connectedDebugAndroidTest`. Реальные Wi-Fi/мобильная сеть, физическое устройство, доступный Cloudflare/Worker endpoint и Telegram E2E — отдельные ручные проверки. **Не объявлять их пройденными без выполнения.** Принятие функции требует не просто компиляции, а подтверждённого прохождения соответствующих автоматизированных тестов; функциональность, требующая внешнего сервера, остаётся с пометкой «E2E не проверен», пока не выполнена проверка.

#### 5.1. Разделение ответственности: Codex и владелец проекта

**Важное прямое указание владельца:** полноценную практическую проверку TGWS-Android на своём физическом Android-смартфоне, включая подключение официального Telegram, работу с реальными Wi-Fi/мобильной сетью, передачу сообщений и медиаданных, смену сети и стабильность длительного соединения, **проводит лично владелец проекта**.

**Codex не должен расходовать время и вычислительный бюджет на самостоятельное ручное тестирование на физическом телефоне**, попытки организовать доступ к личному устройству или ожидание пользовательской проверки до завершения разработки. Не запрашивать устройство, ADB-доступ, видеозаписи и подтверждение каждого этапа перед продолжением. Это не отменяет обязательных проверок кода:

- **Codex выполняет:** JVM/unit/integration tests, Lint, сборку Debug APK, локальные сетевые тесты с воспроизводимыми стендами, доступные Android instrumentation/emulator tests и CI; исправляет выявленные ими дефекты.
- **Владелец выполняет:** установку Debug APK на свой смартфон, проверку официального Telegram, реальных транспортов и переключений сети, фоновой работы, скорости и стабильности в доступной ему сетевой среде; передаёт отчёты по шаблону 3.4.4. От него не требуется приобретать SIM всех четырёх операторов.
- **Обратная связь:** владелец передаст результаты проверок Codex сразу по мере получения. Codex должен использовать эти сообщения для диагностики, исправления дефектов, повторной сборки и выпуска следующего тестового APK, не переписывая работающие компоненты без причины.
- **До получения результатов:** выпускать проверенную автоматическими тестами Debug-сборку с честной пометкой `Проверка владельцем на физическом устройстве: ожидается`. Не считать реальные Telegram E2E, работу в сотовой сети и длительные испытания успешно пройденными.
- **При получении результатов:** учитывать версию APK/commit, Android, сеть/транспорт, конкретный сценарий, ожидаемое и фактическое поведение; запрашивать только недостающие данные, необходимые для воспроизведения. Не просить отправлять токены, MTProto-secret, URL с ключами, закрытые логи или персональную переписку.

**Критерий сдачи задачи Codex:** исправный по доступным автоматическим проверкам Debug APK, ссылка на сборку и отчёт о подтверждённых/неподтверждённых проверках. Положительная физическая приёмка владельцем — отдельный последующий этап, который не должен блокировать завершение текущего прогона Codex или подготовку тестового Pre-release.

### 7. Порядок работы Codex

1. Быстро изучить только относящиеся к ТЗ файлы и `AGENTS.md`, составить компактный чек-лист.
2. Сначала сохранить регрессионные тесты текущей версии; затем реализовывать завершёнными блоками: Fake TLS → Cloudflare/Worker → HTTP/2/media → диагностика → IPv6/network switching → энергосбережение/UI.
3. После каждого блока запускать целевые тесты; перед сдачей — полную Wrapper-команду и CI. Исправлять первопричину ошибок, а не отключать проверки.
4. Для долгой работы фиксировать проверяемые коммиты в отдельной ветке. Если лимит исполнения исчерпан, оставить воспроизводимое состояние, перечень готовых и непроверенных пунктов и точные команды продолжения. Не писать «всё готово» при оставшихся задачах. **Не задерживать передачу Debug APK ради ожидания ручной проверки владельцем: после автоматических проверок предоставить сборку для испытаний и продолжать работу только по доступным задачам/полученной обратной связи.**
5. Не делать force-push, не сливать PR в `main`, не менять архитектуру проекта без необходимости. Не публиковать стабильный `1.0.0`.

**Итоговый ответ Codex на русском:** изменённые файлы/функции, выполненные и проваленные проверки, фактические ограничения и неготовые пункты, URL PR/CI, путь или ссылка на debug APK и версия/commit. Отмечать отдельно **«реализовано в коде»**, **«проверено автоматическими тестами»** и **«подтверждено на физическом устройстве»**.
