# 0.4.2 — Relay Stability Fix

Android 16+ / API 36+, версия 0.4.2, versionCode 19. Изменения продолжают
`feature/0.4.1-diagnostics`; интерфейс и настройки прокси сохранены.

Во время разработки в исходную ветку объединили PR #24: пилотный лимит 6 сессий
и его регрессия сохранены. Эта работа не увеличивает его до 8; остальные пределы
памяти/байтов/очередей не меняются. Облачная устойчивость пилота не подтверждается CI.

## Обнаруженные причины

| Дефект | Изменение | Регрессия |
| --- | --- | --- |
| HTTP Upgrade терял статус и причину отказа | Числовой HTTP status, фиксированная категория, ограниченный Retry-After; без HTTP body/headers/URL | Локальный HTTP/WebSocket peer, неверный Accept, 503 и недоверенный текст |
| При 503 одного Worker каждый DC независимо пробовал занятый endpoint | Общая пауза endpoint для 403/404/429/503 и один probe после паузы; маршрутный backoff сохранён | Разные DC вызывают одно открытие; смена сети сбрасывает бюджет |
| Backoff учитывал только setup: ранний обрыв после Upgrade немедленно повторялся | Ранние отказы без входящих данных попадают в маршрутный exponential backoff; только входящие данные сбрасывают его | Ранний TCP_ERROR и детерминированные 1–30 с / отмена / устаревшие исходы |
| Ошибка записи Close echo подменяла исходный Close | Код и allowlisted reason сохраняются до ответа; сокет закрывается в finally | Полученный Close при намеренно сломанной записи echo |
| Нормальный клиентский EOF закрывал TCP без WS Close | Ограниченный Close handshake перед освобождением raw sockets; stop/network/deadline по-прежнему немедленно abort | Порядок graceful close → abort → raw socket; прежние stop/deadline-тесты |
| Отмена фабрики не закрывала сокет после TCP connect, во время TLS | Фабрика владеет scope на всю жизнь WSS/TCP, проверяет сетевое поколение и закрывает активные scope | Настоящие loopback TCP и прерванный TLS handshake |
| Ошибка Worker до запуска reader-loop оставляла stream-lock | Отмена reader и освобождение обоих locks даже при неудавшемся Upgrade | Исключение accept и повторный допуск без утечки |
| Worker освобождал слот при закрытии WS до завершения TCP close | Слот освобождается один раз, после подтверждённого закрытия обоих ресурсов | Задержанное TCP close не допускает лишнего dial |
| Отказ одной сессии скрывал другие работающие сессии того же маршрута | Живой маршрут остаётся AVAILABLE, отдельная сессия получает собственную причину | Две сессии, закрытие одной, затем смена сети |
| Поздний EOF мог изменить backoff уже после смены сети | Runtime-исход привязан к поколению исходного permit и учитывается один раз | Устаревший EOF и повторный исход не меняют бюджет новой сети |

Успешный Upgrade не доказывает доставку сообщений Telegram. Устранение этих
воспроизводимых дефектов не подтверждает исправление всех разрывов в реальной сети.

## Диагностика

В «Диагностика → Весь журнал» и JSON schema 3:

- `upgrade.status`, `failure`, `relay_reason`, `retry_after_ms`;
- `retry_ms` — оставшаяся пауза на момент наблюдения, а не постоянно обновляемый таймер;
- `session.id` — порядковый номер внутри запуска сервера, не идентификатор пользователя;
- `reason`, `established`, `duration_ms`, `sent`, `received`, `close_code`, `close_reason`.

Причины разделяют клиентский EOF/IO/повреждённый пакет, удалённый EOF/IO/Close,
отказ setup, backoff, handshake/connect/idle/write timeout, смену сети и остановку.
Logcat дополнительно ограничен 8 событиями сессий и 32 записями всего в секунду;
в журнале остаются последние 128 событий независимо от ограничения logcat.
Очередь закрытий сессий между ядром и UI также ограничена 128 записями: при занятом main thread
сохраняются последние события, а обработка выполняется одним ограниченным пакетом
за задание, без отдельного Handler callback на каждую закрытую сессию.
Байты сессии относятся к локальному транспортному потоку; это не подтверждение
доставки сообщения Telegram. История ограничена 128 событиями в памяти.
Экспорт — только после действия пользователя. Адреса, токены, ключи,
MTProto-пакеты и произвольные строки исключений не сохраняются.

| HTTP / категория | Значение |
| --- | --- |
| 503 / CAPACITY | Все шесть слотов isolate заняты, включая закрывающиеся соединения; Retry-After 2 с |
| 503 / CONFIGURATION | В Worker отсутствует корректный Secret TGWS_RELAY_TOKEN |
| 502 / UPSTREAM_CONNECT | Worker не открыл TCP к выбранному DC |
| 504 / UPSTREAM_TIMEOUT | Срок открытия upstream TCP истёк |
| 404 без категории | Путь, токен, DC или Upgrade не прошли проверку; не публикуйте URL |
| 403/429/5xx без категории | Отказ HTTP без машинной категории; по одному статусу нельзя установить механизм фильтрации |

`BYTE_LIMIT` и `IDLE_TIMEOUT` отражают известное ограничение/простой сессии,
а не недоступность всего реле. Они остаются видимыми в журнале. Непредвиденные
TCP_ERROR, WS_ERROR, ошибки TLS и протокола не скрываются.

## Обновление существующего Worker

Обновление APK **не обновляет** код в аккаунте Cloudflare.

1. В успешном запуске **Android CI** для PR 0.4.2 скачайте артефакт
   `TGWS-Cloudflare-Worker-<checked SHA>`. В нём `worker.js`, `SHA256SUMS`
   и `build-info.json`. Сверьте `source_commit` с PR/APK, а SHA-256 файла — с checksum.
2. Откройте **существующий** Worker → Edit code в панели Cloudflare.
   Замените весь модуль содержимым `worker.js`. Не вставляйте Markdown-ограждения.
3. Сохраните существующие имя Worker, домен/route и Secret `TGWS_RELAY_TOKEN`.
   Не создавайте новый токен и не меняйте MTProto secret в приложении.
4. Deploy. Оставьте observability/Workers Logs выключенными: путь содержит секрет.
   Для Wrangler используйте `npm ci --ignore-scripts --no-audit --no-fund`,
   `npm test`, `npm run build`, затем `npm run deploy` из `cloudflare-worker/`
   в своём аккаунте. Исходный код и сборка не выполняют deploy автоматически.
5. Установите тестовый APK поверх 0.4.1 с той же Debug-подписью. Не удаляйте
   приложение: это удалит его данные и ключи. При несовместимой подписи остановитесь.
6. Остановите и заново запустите локальный прокси; адрес и секрет должны сохраниться.
   Старый модуль `worker-v0.1.0-alpha` не содержит этих изменений.

Новый APK совместим со старым Worker, но дополнительные категории HTTP появятся
только после deploy нового модуля. Протокол, маршруты DC и токен пути не изменены.

## Сохраняемые ограничения и проверка владельцем

- **6 сессий/isolate**, очередь **4 МиБ + 4 Б**, **64** сообщения и **16 МиБ суммарно
  в обе стороны/сессию** сохранены. Это не глобальная квота аккаунта.
- Worker WebSocket.send не предоставляет drain/backpressure. Нельзя безопасно
  обещать непрерывную передачу больших медиа без отдельного flow-control протокола.
  Закрывающиеся WS держат слот до подтверждения платформы; слот не освобождается
  вслепую по таймеру. Если close не приходит, 503 остаётся безопасным отказом.
- Нет автоматического replay MTProto-пакетов или бесконечного retry; Telegram
  создаёт новую сессию после обрыва. Прямой fallback в режиме «Только реле» запрещён.
- Системный DNS, TLS/hostname verification, minSdk 36 и Keystore сохранены.
- Внешний Worker не развёртывался из этой среды. Проверка на личном устройстве — владелец.

После обновления APK **и** Worker: проверить сообщения в обе стороны, несколько
циклов start/stop, фон, смену сети и восстановление. Отдельно проверить фото/кружки
и передачу до/через 16 МиБ, различая ожидаемый BYTE_LIMIT и остальные ошибки.
При сбое: открыть журнал, просмотреть безопасный отчёт и передать категорию,
HTTP/Close-код и номер тестовой сборки. Не публиковать устройства, операторов,
частные адреса, токены или сообщения.

Официальные API, сверенные при аудите:
[WebSockets](https://developers.cloudflare.com/workers/runtime-apis/websockets/),
[TCP sockets](https://developers.cloudflare.com/workers/runtime-apis/tcp-sockets/).
Binary mode и обработчики задаются до accept; Socket.close закрывает обе стороны TCP.
